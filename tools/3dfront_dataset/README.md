# Подготовка MIDI-3D/3D-FRONT для бенчмарка

Одна точка входа — `prepare.py`. В `_lib/` находятся рабочие модули экспортёров: разные модели требуют разные форматы разметки.

Нужен Python 3.9+ и `pip install -r tools/3dfront_dataset/requirements.txt`.
Все команды ниже выполняются из корня репозитория. Blender нужен только на шаге
рендера; подготовка и проверка разметки работают на CPU.

## Зафиксированная выборка

`freeze` строит разбиение из любого источника, поэтому размер набора определяется тем,
что подано на вход. В репозитории лежит одно конкретное разбиение — то, на котором
получены опубликованные числа:

| Split | Комнаты | Панорамы (4 на комнату) |
| --- | ---: | ---: |
| train | 663 | 2652 |
| val | 148 | 592 |
| test | 141 | 564 |
| Всего | 952 | 3808 |

Источник — `3D-FRONT-TEST-SCENE` репозитория
[huanngzh/3D-Front](https://huggingface.co/datasets/huanngzh/3D-Front); это **наше**
разбиение, не официальные train/val/test MIDI. Списки ID лежат в `splits/*.txt`,
причины исключений и ожидаемое число комнат — в `splits/excluded_rooms.json`,
и загрузчик сверяется именно с ним. Другой источник даёт своё разбиение и свои числа.

Дома не пересекаются между split: комнаты одной квартиры целиком попадают в одну часть.
Исходные GLB не удаляются. Разделение по ID дома само по себе не доказывает
отсутствия геометрических дубликатов под разными ID.

Разбиение строит команда `freeze`; она же применяет правила исключения:

```bash
python tools/3dfront_dataset/prepare.py freeze /data/3D-FRONT-TEST-SCENE \
  --metadata /data/front3d/state/source_metadata.json
```

Отбраковываются комнаты, у которых не восстанавливается геометрия, схлопнулся контур,
площадь пола меньше квадратного метра, мебель не сходится на одном масштабе или негде
поставить требуемое число камер. Последнюю проверку `freeze` выполняет тем же кодом
отбора, что и рендерер, но без Blender: расстояние до поверхностей считается по точкам,
насэмплированным с треугольников. Полное совпадение с рендерером не гарантируется —
`--plan-only` остаётся окончательной проверкой, и редкий отказ там всё ещё возможен;
тогда `freeze --force` запускают повторно, чтобы дописать его в исключения.

Команда отказывается перезаписывать существующее разбиение без `--force`: подменить его
незаметно значит сделать прежние числа несопоставимыми с новыми.

## Полный запуск

`/data/front3d-experiment` должна быть новой папкой.
`init` проверяет наличие и геометрию всех комнат до создания эксперимента.

```bash
python tools/3dfront_dataset/source_metadata.py \
  /data/raw/3D-FRONT.zip /data/3D-FRONT-TEST-SCENE \
  /data/front3d-experiment/state/source_metadata.json
python tools/3dfront_dataset/prepare.py init \
  /data/3D-FRONT-TEST-SCENE /data/front3d-experiment
python tools/3dfront_panorama_renderer/run_batch.py \
  /data/front3d-experiment/splits/rooms.jsonl /data/front3d-experiment/plan \
  --views 4 --plan-only
python tools/3dfront_panorama_renderer/run_batch.py \
  /data/front3d-experiment/splits/rooms.jsonl /data/front3d-experiment/outputs
python tools/3dfront_dataset/prepare.py export /data/front3d-experiment \
  --scale-table /data/front3d-experiment/state/source_metadata.json \
  --class-table /data/front3d-experiment/state/source_metadata.json
python tools/3dfront_dataset/prepare.py validate /data/front3d-experiment
```

Для уже отрендеренного эксперимента с этим split начинайте с `export`.
Можно запустить один этап через `--stage rgb|ground_truth|relations|shape|crops|coco|horizonnet|dpc`.
Зависимости: RGB → ground_truth → остальные экспортёры. Используйте новую папку
эксперимента при смене исходников/рендера: существующие PNG и ссылки переиспользуются.

## Результаты

| Папка в эксперименте | Содержимое |
| --- | --- |
| `rgb/`, `manifests/` | PNG и JSONL со всеми sample_id |
| `ground_truth/`, `manifests_gt/` | 3D bbox предметов и layout для toolbox |
| `coco/` | train/val/test JSON: 2D bbox и instance masks (RLE), 8 классов |
| `horizonnet/` | изображения и dense NPZ: границы пола/потолка, вероятности углов |
| `dpc_dataset/` | ссылки на RGB, split JSON, соответствие имён исходным sample_id |
| `objects/` | по папке на модель: меши, выборки знакового расстояния, вырезки |
| `state/` | машиночитаемые результаты экспортов и проверок |
| `validation/` | необязательные локальные отчёты и изображения для просмотра |

Папки `dpc_dataset` достаточно для подачи изображений в DPC, **не для полного
переобучения** BEN/LDIF/MGN/Scene-GCN: их специфические обучающие targets
требуют отдельной подготовки. Экспорт не означает, что все сети уже обучены.

Классы берутся из исходного 3D-FRONT: десять обучающих категорий, а подробное название
из семидесяти двух сохраняется в `attributes.fine_class`. Список пишется в
`state/classes.json`, и все экспортёры читают его оттуда.
Маски получаются из рендера автоматически; 3D bbox — PCA по исходной геометрии
в системе камеры (Z вверх). Вручную обводить тысячи кадров не нужно.

Разметка приведена к метрам: комнаты источника нормированы каждая своим
масштабом, поэтому на комнату восстанавливается один множитель — по точной таблице
из исходного 3D-FRONT (`--scale-table`), а без неё по высоте потолка
(`--reference-height`). Отчёт по комнатам — `state/metric_scale.json`.

Layout-target — вертикальное вытягивание реального контура пола между двумя
представительными высотами. Он поддерживает непрямоугольные комнаты, но
**не является точной разметкой многоуровневых/декоративных потолков**.
В legacy `LayoutIoU3D` используется охватывающий AABB, не объём этого контура.
Точность метрического масштаба при работе от высоты потолка ограничена
отклонением потолка конкретной комнаты от принятого значения.
Предмет, пересекающий шов панорамы, размечается в кадре, сдвинутом на полширины,
где он целен: сравниваемые методы так же прогоняют детектор по исходному и
сдвинутому кадру и сшивают результаты. Поэтому в `coco/` на одну панораму
приходится до двух изображений, различаемых полем `panorama_frame`; сдвинутый кадр
пишется рядом с исходным как `<вид>.frame1.png`. Предмет, разрезанный швом в обоих
кадрах, делится на части с плотными рамками. Значения COCO AP здесь — наблюдение за
ходом обучения, а не показатель бенчмарка.

## Проверка и просмотр

```bash
python tools/3dfront_dataset/audit.py \
  /data/front3d-experiment/splits/rooms.jsonl \
  /data/front3d-experiment/outputs \
  /data/front3d-experiment/validation/geometry --workers 4
python tools/3dfront_dataset/review.py \
  /data/front3d-experiment/validation/geometry \
  /data/front3d-experiment/validation/review --all-flagged
```

`audit.py` проверяет камеры/геометрию и яркость/валидность depth, создаёт
`review.html` и превью с линиями layout. `review.py` собирает контактные листы:
все отмеченные проблемы геометрии, потолка, крупных объектов и RGB плюс
фиксированную случайную выборку. `--all` добавляет каждую комнату.
Флаг `missing_depth` означает менее 95% валидных depth-пикселей; он не доказывает
отсутствия самого depth-файла. Контактные листы не заменяют разбор таких пикселей.

`validate` проверяет размеры/числа dense-разметки, точное совпадение sample_id,
COCO RLE/классы/bbox и ссылки DPC. Это проверка форматов и согласованности,
а не автоматическое одобрение качества или обучающих результатов.
`state/training_gate.json` остаётся закрытым до отдельного решения после QA.
